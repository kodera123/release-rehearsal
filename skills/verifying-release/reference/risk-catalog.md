# 変更種別ごとのリスクカタログ

各種別について「典型リスク / 確認方法 / 用意する汚いデータ / 本番確認クエリの例」。該当する節だけ読む。
SQL は PostgreSQL 想定。他 DB は読み替える。**本番の DB 種類・バージョンが未確認なら、挙動が DB で分かれる点は両方の条件を書き、両方の確認クエリを出す。**

---

## DB migration

| リスク | 確認方法 | 汚いデータ / 本番確認 |
|---|---|---|
| 制約追加（NOT NULL / UNIQUE / FK / CHECK）が既存データで失敗し、デプロイが止まる | 汚いデータを入れた DB で migrate。UNIQUE は index 定義が大文字小文字を区別するか（`lower()` / citext の有無）で、失敗する重複・すり抜ける重複が変わる点を確認 | 対象列が NULL の行、重複行（大文字小文字違い・前後空白を含む）、参照先が消えた孤児行。本番: `SELECT col, count(*) FROM t GROUP BY 1 HAVING count(*) > 1;` / `... WHERE col IS NULL` |
| default 付きカラム追加で、既存行の意味が変わる（例: 全件 `confirmed` になるが、実はキャンセル済みのものがある） | 既存の表現（`canceled_at` など）ごとに件数を出し、default と矛盾しないか確認 | 旧表現の各パターンの行 |
| テーブルロックで本番の書き込みが止まる（index 作成・型変更・default の書き換え） | `concurrently`・`disable_ddl_transaction!` の有無、DB バージョンごとの挙動を確認（例: PostgreSQL 11+ は定数 default 付きカラム追加がメタデータ変更のみ、10 以下はテーブル書き換え） | 本番: 対象テーブルの件数とサイズ `SELECT pg_size_pretty(pg_total_relation_size('t'));` |
| カラムの削除やリネームで、デプロイ中の旧コードが落ちる | 旧コードがそのカラムを参照していないか（`ignored_columns` などの段階的な削除か） | — |
| ロールバックできない | `down` の有無と、データ変換が可逆か | — |
| backfill が大量の行で遅い、またはタイムアウトする | バッチ処理か、実行場所（migration 内かタスクか） | 本番の件数 |

## API レスポンス・リクエスト形式

| リスク | 確認方法 |
|---|---|
| 旧形式を期待する呼び出し元が壊れる（フロントの別画面、モバイル、外部連携、Webhook の受け手） | 呼び出し元をすべて grep。外部利用者の有無はユーザーに確認 |
| デプロイ直後、古い JS バンドルを開いたままのユーザーが壊れる | 旧フロント × 新 API の組み合わせを考える（ローリング中は新フロント × 旧 API もありうる） |
| ページネーション導入で「全件取れる」前提の処理が黙って欠ける（CSV 出力・集計・セレクトボックス） | 1 ページを超える件数のデータで確認 |
| 必須パラメータの追加や、バリデーションの強化で、既存のクライアントが 4xx になる | 旧リクエストをそのまま送る |

## バックグラウンドジョブ

| リスク | 確認方法 | 本番確認 |
|---|---|---|
| 引数の追加・削除・順序変更で、デプロイ前に積まれたジョブや retry 中のジョブが `ArgumentError` になる | 新しい引数にデフォルト値があるか。旧引数でジョブを手動 enqueue して実行 | キュー・retry・scheduled に残っている対象ジョブの件数（Sidekiq なら `Sidekiq::Queue` / `RetrySet` / `ScheduledSet`） |
| ローリング中に、旧ワーカーが新しい形式のジョブを受け取る | 旧コードが新しい引数を受け付けるか | — |
| 冪等でない処理を再実行し、二重送信や二重課金になる | retry 時の挙動 | — |
| cron やスケジュールの変更で、実行漏れや重複実行が起きる | 切り替え時刻をまたぐケース | — |

## UI・フロントエンド

| リスク | 確認方法 |
|---|---|
| 共有コンポーネントの変更が他画面に波及する（作成と編集、一覧とダッシュボード） | import 元を grep し、使っている画面ごとにスクショを撮る |
| 既存データの表示崩れ（長文、NULL、旧 enum 値、0 件、大量件数） | 汚いデータで表示する |
| 権限・ロールによる出し分け | 各ロールでログインしてスクショを撮る |
| 状態の復元（ブラウザバック、リロード、URL 直打ち、下書き） | 手順に含める |

## 設定・環境変数・依存

| リスク | 確認方法 |
|---|---|
| 新しい環境変数が本番で未設定、またはフィーチャーフラグの初期値が誤っている | 参照箇所と、未設定時の挙動（例外か、デフォルト値か）を確認。本番に設定済みかはユーザーに確認 |
| gem や npm パッケージのメジャー更新による挙動変更 | CHANGELOG の breaking changes |
| キャッシュキーやシリアライズ形式の変更で、旧キャッシュ・旧セッション・旧 Cookie が読めない | 旧形式の値が残った状態で起動する |

## 権限・認証・データ可視範囲

| リスク | 確認方法 |
|---|---|
| スコープ条件の変更で、他テナントや他ユーザーのデータが見える／自分のデータが見えなくなる | テナントを 2 つ作り、相互に見えないことを確認 |
| 既存ユーザーのロールや状態が、新しい判定条件に当てはまらない | 既存の各ロール・状態の組み合わせで確認 |

## 集計・通知・外部送信

| リスク | 確認方法 |
|---|---|
| 集計条件の変更で、過去の数値が変わる | 変更前後で同じデータの集計結果を比べる |
| 通知やメールが既存ユーザーに一斉に送られる（新しい条件に既存データが一括で当てはまる） | 本番で新しい条件に当たる件数をクエリで出す |
| 外部 API（決済・メール・SMS）の送信先や内容が変わる | サンドボックスで確認。本番では送らない |

## 日時・タイムゾーン・期間の境界（毎回確認）

**洗い出し手順:** 差分から日時を扱う箇所を grep し、コマンドと結果を `logs/<ID>-datetime-grep.txt` に保存する。ヒットした箇所ごとに下表のリスクを当てる。0 件なら「該当なし」として項目に残す。

```bash
P='\b(date|dates|datetime|time|times|timestamp|timestamps|timezone|time_zone|tz|now|today|yesterday|tomorrow|ago|since|from_now|in_time_zone|beginning_of_[a-z]+|end_of_[a-z]+|strftime|strptime|iso8601|toISOString|toLocale[A-Za-z]*String|dayjs|moment|luxon|DateTimeFormat|cron|interval|date_trunc|current_date|current_timestamp|expires?_at|expired?|deadline|[a-z_]+_(at|on|date))\b|Date\.|new Date|Time\.|DateTime\.|date-fns|at time zone'
# 追加・削除行のうち日時を扱う行
git diff <本番ref>..<release ref> -U0 | grep -E '^[+-][^+-]' | grep -Ei "$P"
# 日時を扱う変更を含むファイル（項目はファイル単位で作る）
git diff <本番ref>..<release ref> --name-only | while read f; do git diff <本番ref>..<release ref> -U0 -- "$f" | grep -E '^[+-][^+-]' | grep -qEi "$P" && echo "$f"; done
```

パターンは Ruby / JS / SQL の一般的な名前を想定している。プロジェクト独自の日時ユーティリティがあれば `P` に足す。

| リスク | 確認方法 | 汚いデータ / 本番確認 |
|---|---|---|
| 保存（UTC など）と表示・集計（JST など）のタイムゾーン変換が漏れ、日付が 1 日ずれる | 基準タイムゾーンの 0:00 直後の時刻のデータ（JST なら 0:00〜8:59 = UTC では前日）で表示・検索・集計する | 境界時刻の行。本番: サーバー・DB・アプリそれぞれのタイムゾーン設定（`SHOW timezone;` など） |
| 期間の端の扱い（終了日を含むか、`<` と `<=`、`23:59:59` で切るか翌日 0:00 未満で切るか） | 期間の最初と最後の瞬間（`23:59:59.999` を含む）のデータで確認 | 期間の両端ちょうどの行 |
| 月末・年末・うるう年・年度の切り替え（1/31 の 1 か月後、2/29、12/31 → 1/1、年度始め） | 該当日付を入力・計算させる。時刻を固定できるなら固定して実行 | 月末日・2/29 の行 |
| 日付だけの文字列の解釈がずれる（例: JS の `new Date("2026-10-08")` は UTC 0 時扱いで、JST 以外の表示では前日になりうる） | ブラウザ・サーバーのタイムゾーンを変えて表示する | — |
| date 型と timestamp 型の混在、文字列の日付比較 | 型と比較箇所をコードで確認 | — |
| バッチ・cron の実行時刻と「今日」の定義のずれ（UTC で動く cron が JST の前日を処理する） | スケジュール定義のタイムゾーンを確認し、境界時刻に実行したときの対象範囲を確かめる | 本番: スケジューラーのタイムゾーン設定 |
| 夏時間のある地域の利用者（存在しない時刻・2 回ある時刻） | 利用者のタイムゾーンを Step 0 で確認し、該当する場合だけ確認 | 本番: 利用者のタイムゾーン分布 |
| 有効期限・締め切りの判定がタイムゾーンや境界でずれる（期限当日に使えない／翌日まで使える） | 期限ちょうど・直前・直後で確認 | 期限が境界にあるデータ |

## 性能（オプション: Step 0 で含めると決めた場合のみ）

| リスク | 確認方法 | 汚いデータ / 本番確認 |
|---|---|---|
| 一覧やループの中で関連データを 1 件ずつ取得する（N+1） | 一覧を N 件ある状態で開き、発行クエリ数をログで数える（件数を増やしてクエリ数が比例して増えないか） | 本番相当の件数 |
| 新しいクエリが大きいテーブルを全件走査する | 本番に近い件数のデータで `EXPLAIN` を取り、実行計画を `logs/` に保存 | 本番: `EXPLAIN <クエリ>`（`ANALYZE` は付けない。クエリを実際に実行してしまう） |
| 新しい検索条件・並び替えの列にインデックスが無い | schema と migration でインデックスの有無を確認 | 本番: 対象テーブルの件数とインデックス一覧 |
| ページングの無い全件読み込みで、メモリや応答時間が膨らむ | 大量件数のデータで応答時間を計測 | 本番の件数 |
| 外部 API 呼び出しの追加で、応答が遅くなる・タイムアウトする | タイムアウト設定と、同期か非同期かを確認 | — |
