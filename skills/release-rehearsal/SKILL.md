# Release Rehearsal

リリース対象の差分に対して、**動作確認リスト → 十分性レビュー → エビデンス付き実行 → 既存データ/機能の影響判定** を行い、Go / 条件付き Go / No-Go を根拠付きで渡す。

前提となる姿勢: 証拠（実行したコマンドの出力・保存したファイル）を自分の目で確認するまで「OK」「通った」と書かない。検証環境の起動手順は repo の README・開発環境の手順に従う。

## 鉄則

1. **エビデンスはファイルとして残す。** ブラウザ操作ツールの多くは、スクショを撮っても画像がエージェントに返るだけで**ファイルは残らない**。保存先パスを指定できる手段（Step 4）で撮り、`ls` で実在を確認する。
2. **十分性を自己採点しない。** リストを作った本人の「十分です」は根拠にならない。独立したサブエージェントにリスク洗い出しをさせて突き合わせる（Step 3）。
3. **seed で migrate が通った ≠ 既存データ OK。** 本番に存在しうる「汚いデータ」を作ってから migrate / 実行する（Step 5）。
4. **未実施は消さない。** 実施できなかった項目は `未実施` のままリストに残し、判定に必ず反映する。未実施が残るのに「Go」は出さない。
5. **本番（DB・環境・キュー）には触らない。** 確認が要るものは read-only のクエリ/コマンドを用意してユーザーに実行を依頼する。
6. **検証中に見つけた不具合を黙って直さない。** `NG` として記録し、修正するかはユーザーに諮る（修正したら該当項目を再検証し、両方の結果を残す）。
   - **NG の定義**: release のコードが、本番で起こりうる条件（滞留ジョブ・旧バンドル・既存データなど）で誤動作することを再現、またはコード上で確定したもの。「本番でその条件が成立するか未確認」でも NG として扱い、影響表（R）にも載せる

## 手順

```
[0] 前提確認 ─── 対象差分・本番の前提を確定。不明点はまとめて質問
[1] 差分の棚卸し ─ 変更を種別に分類（migration / API / UI / job / 設定 …）
[2] 動作確認リスト作成 ─ 変更 → リスク → 確認項目 の順で逆算
[3] 十分性レビュー ─ 独立サブエージェントとの突き合わせ + 判断理由
[4] 実行 ─── スクショ / テキストエビデンスを保存しながら 1 項目ずつ
[5] 既存データ・既存機能の影響判定 ─ 汚いデータで再現 + 本番確認用クエリ
[6] レポート ─── 判定 + 条件 + 未確認事項
```

### Step 0: 前提確認

- 対象: `git log <本番ref>..<release ref>` の範囲を確定（本番 ref = 本番タグ / main / 本番デプロイ済み SHA。どれかを確認）
- 以下は**推測で埋めず**、repo・インフラ定義で確定できなければ**1 回にまとめて**ユーザーに聞く。聞けない間も調べられる作業は進める:
  - デプロイ方式（ローリング / 一括 / メンテ停止あり）と migrate のタイミング
  - DB の種類・バージョン、主要テーブルの概算件数
  - API の外部利用者・モバイルアプリ・古いフロントバンドルの存在
  - ジョブキューの滞留・retry・scheduled の有無
  - 検証環境（ローカル / staging）と使ってよいデータ
  - サービスの基準タイムゾーンと、利用者のタイムゾーン（日時境界の確認に使う。Step 2）
  - **性能確認を含めるか（オプション）**。含める場合は risk-catalog の「性能」節を使う。含めない場合はレポートに「性能確認: 対象外（ユーザー判断）」と書く
- 返事が来ないまま進める場合は、前提を**「仮定: 〜（未確認）」としてレポートに明記**し、その仮定に依存する判定は Go にしない
- **所要時間を見積もる**（根拠: 項目数 × 1 項目あたりの想定時間 + 環境準備。見積もりの式ごと伝える）。残り時間で Step 5 まで終わらないなら、この時点で「判定の上限は条件付き Go」とユーザーに伝える（「急いでいるので結論だけ」と言われても、未確認を Go に丸めない）
- エビデンス保存先を決める: `<repo>/tmp/release-rehearsal/<YYYYMMDD>-<ref>/`（`git check-ignore` で ignore 済みを確認。されていなければ repo の外の `~/release-rehearsal/<repo名>/<YYYYMMDD>-<ref>/`）

### Step 1: 差分の棚卸し

`git diff --stat` の**全ファイル**を種別に振り分ける。流し読みした「その他」を作らない。1 ファイルずつ「どの種別か / 振る舞いが変わるか」を書く。

### Step 2: 動作確認リスト作成

変更ごとに **想定リスク → 確認項目** を書く。項目から始めない。
種別ごとの典型リスクは [reference/risk-catalog.md](reference/risk-catalog.md) を引く（migration・API 形式・ジョブ引数・キャッシュ・権限・日時 など）。

必ず含める:
- **新機能の正常系・異常系・境界値**
- **間接影響**: 変更したコード/コンポーネント/クエリの呼び出し元（grep で洗う）
- **既存データ起点の項目**: 変更前から存在するデータでの表示・編集・集計
- **日時・タイムゾーン・期間の境界**（毎回）: 差分の日時処理を risk-catalog「日時」節の手順で洗い出し、該当する境界を項目にする。日時処理が差分に無い場合も、洗い出しの grep 結果を `logs/` に保存し「該当なし」を項目として残す
- **業務クリティカル導線の回帰**（差分に触れていなくても最低限）

オプション（Step 0 で含めると決めた場合のみ）:
- **性能**: risk-catalog「性能」節

列は [reference/report-template.md](reference/report-template.md) の形式（ID / 対象変更 / 潰すリスク / 手順 / 期待結果 / 結果 / エビデンス）。

### Step 3: 十分性レビュー

1. 突き合わせ表: 差分の全ファイル → 対応する項目 ID、または「確認不要の理由」。空欄 = ギャップ
2. **独立レビュー**（Step 1 と並行で走らせてよい）: サブエージェントに `git diff <本番ref>..<release ref>` の実行方法（repo パスと ref）と Step 0 の前提（未確認は未確認と書く）だけを渡し（リストは渡さない）、「本番で壊れうるシナリオ」を列挙させる。自分のリストで潰せていないものをギャップとして扱う
3. ギャップはリストに追加するか、「残存リスク」として理由付きで残す
4. 判断理由を書く: どのリスクをどの項目で潰したか / 何を意図的に外したか（理由） / 残存リスクと発生条件。**「十分」と書くなら、残存リスクが許容できる理由を書く**

リスト確定時点で一度ユーザーに見せる（実行は待たずに進めてよい。指摘があれば反映）。

### Step 4: 実行

- 画面: 保存先パスを指定できる手段で `<保存先>/screenshots/<ID>-<短い説明>.png` に保存する（パスは**絶対パス**で）。操作前後の比較が要る項目は `-before` / `-after` を撮る
  - 例: chrome-devtools MCP の `take_screenshot`（`filePath` 指定）、Playwright スクリプトの `page.screenshot({ path })`
  - 画像がエージェントに返るだけでファイルに残らないスクショ手段は、エビデンスの代わりにならない
  - 実在の個人情報（顧客名・メール等）が写る画面は、テスト用データで撮るか、マスクしてから保存する
- 画面に出ないもの（API・ジョブ・migration・ログ）は無理に画面化せず、コマンドと出力を `<保存先>/logs/<ID>-*.txt` に保存
- 1 項目ごとに結果を `OK / NG / 未実施(理由)` で記録。NG は再現手順と実際の結果も残す
- 最後に `ls <保存先>/screenshots` で、リストのエビデンス列と実ファイルが一致することを確認する。さらに**各項目から最低 1 枚を開いて**、ログイン画面やエラー画面を撮っていないか中身を確かめる

### Step 5: 既存データ・既存機能の影響判定

1. **本番 ref の状態で DB を作り、汚いデータを入れる** → release に切り替えて migrate → 既存データで Step 4 の該当項目を再実行。
   - **ユーザーの開発用 DB を上書きしない。** reset / drop が必要ならユーザーに確認する。用意する方法は次の優先順:
     1. 検証用 worktree（`git worktree add`）に、開発用とは**別のポート・別の DB** で独立した環境を立てる（立て方は repo の開発環境手順に従う。画面の確認もできる）。マシンのリソースが足りなくても、ユーザーや他作業の環境を勝手に止めず、どれを止めてよいかユーザーに諮る
     2. 画面が要らない確認（migrate の成否・既存データへの変換結果）だけなら、既存の DB サーバー内に別名 DB（例: `<db>_relverify`）を作り、`DATABASE_URL=... <migrate コマンド>` のように**1 回限りの環境変数**で向ける（`.env` や環境設定ファイルは書き換えない）
   - 本番 ref のコードは `git worktree add` で別ディレクトリに出す（作業中の worktree で checkout を往復しない）
   - 汚いデータの例は risk-catalog の各項目にある（重複・NULL・大文字小文字違い・旧 enum 値・論理削除済み・巨大データ・日付境界の時刻）
2. **旧コード × 新データ / 新コード × 旧データ** の両方向を考える（ローリングデプロイ中・ロールバック時・滞留ジョブ）
3. 本番に対して確認が要る点は read-only クエリ/コマンドにしてレポートに載せる（ユーザーが実行）
4. 結果は「不具合が出る条件」として書く: **条件 / 起きること / 影響範囲 / 発生可能性とその根拠 / 回避策**。条件が本番未確認なら「未確認」と明記

### Step 6: レポート

[reference/report-template.md](reference/report-template.md) に沿って `<保存先>/report.md` を書く（正本）。

共有用ページは任意。HTML ページを公開できる環境（例: Claude.ai の Artifact）があれば、report.md を元にページを作り、スクショを同梱して公開しリンクを渡す。無ければ report.md と `screenshots/`・`logs/` をそのまま共有する。どちらの場合も、スクショに実データが写っているなら共有前にユーザーに確認する。

判定基準（**上から順に評価し、最初に当てはまったものが判定**）:
| 順 | 判定 | 条件 |
|---|---|---|
| 1 | **No-Go** | 未修正の NG があり、ユーザーが**明示的に**リスク受容していない（返事が無い = 受容ではない）。または、不具合の発生条件が**特定できていない**／本番で成立したときの**回避策が無い** |
| 2 | **条件付き Go** | 未実施・未確認・仮定・受容済み NG が残るが、それぞれ「リリース前に何を確認し、結果がどうなら Go か」（例: 本番で Q1 が 0 行）と回避策が書けている |
| 3 | **Go** | NG・未実施・未確認なし。残存リスクすべてに許容理由がある |

**回避策** = リリース前、またはデプロイ手順の中で実施できる予防策（データ掃除・キューを空にする・フラグ OFF でデプロイ など）。ロールバックや事後修正は回避策に数えない。

## Red Flags — 止まってやり直す

- 「スクショ撮りました」なのに保存先に `.png` が無い
- 「seed で migrate 通ったので既存データ OK」
- 十分性の根拠が「全変更に項目がある」だけ（リスクで語っていない）
- 未実施の項目がリストから消えている / 判定に反映されていない
- 日時境界の項目が無い（「該当なし」なら grep 結果のログが無い）
- 本番の前提（DB バージョン・デプロイ方式・外部利用者・タイムゾーン）を推測で書いている
- 時間が無いので独立レビューを省いた
- 「急いでいる」と言われて、未確認の前提を Go に丸めた
- 検証用 DB を作るためにユーザーの開発用 DB を reset / drop した

## 時間が足りないとき

削る順（下から削る）。削った項目は `未実施` として残し、判定は最大でも「条件付き Go」。1 と 2 すら終わらない場合は、終わった範囲・終わっていない範囲を明記して**判定は No-Go（検証未完了）**とし、残作業の見積もりを添える。
1. 残す: migration / 既存データの影響判定と本番確認クエリ（デプロイ停止・データ破壊のリスク）
2. 残す: 互換性と日時境界の机上確認（API 呼び出し元・ジョブ引数・キャッシュ・日時処理の grep）— コードを読むだけで安い
3. 残す: 独立レビュー（サブエージェントに並行で走らせれば時間はほぼかからない）
4. 削る候補: UI の網羅的なバリデーション・境界値のスクショ（代表 1 件 + テキストで代替）
5. 削る候補: 差分と無関係な回帰の網羅
